Decisions:
1. Rule Data Structure: use a small sealed rule hierarchy for type safety and readable exhaustive evaluation. Keep Phase 1 minimal: allow/deny decisions from role, group, and custom attribute rules. Avoid map-only untyped rules as the primary API.
2. Attribute Matching Logic: use deterministic exact matching in Phase 1. Combine attributes within a rule with AND semantics. Multiple rules are evaluated in explicit list order. No regex, wildcard, or expression language in Phase 1.
3. Audit Record Format: return a structured audit record with request id, user id, entitlement id, decision, matched rule ids, evaluated rule ids, deny/allow reason, and timestamp. Keep it in memory and queryable later by future phases.
4. API Design: expose a small Kotlin API centered on EntitlementValidator plus plain Kotlin data classes. Prefer direct construction and simple immutable config over complex builders for Phase 1.
5. Entitlement Input Model: validate a single rich request object, not batch validation. Request includes user id, entitlement/feature id, roles, groups, and custom attributes. Batch validation is out of scope.
